qa:
  - q: "모델 학습과 서빙은 무엇이 다른가요?"
    a: "학습은 수 시간에서 수 일 걸리는 1회성 배치 작업이고 정확도나 Loss로 평가하며, 실패하면 다시 돌리면 됩니다. 서빙은 24시간 상시로 밀리초 단위 응답을 해야 하고 지연시간·처리량·가용성이 핵심 지표이며, 실패하면 곧바로 서비스 장애가 됩니다. 그래서 학습 코드는 실험적으로 자주 바뀌어도 되지만 서빙 코드는 변경에 신중해야 하고, 장애 시 재실행이 아니라 즉시 롤백이나 Fallback이 필요합니다."
  - q: "AIOps는 왜 필요한가요?"
    a: "일반 소프트웨어는 버그가 나면 에러가 나지만 AI 서비스는 에러 없이 틀립니다. 데이터는 업무의 결과라 업무 환경이 바뀌면 입력 분포가 바뀌고, 모델은 HTTP 200을 돌려주면서 예측만 나빠집니다. AIOps는 지연시간·에러율·예측 오차를 자동으로 수집하고, 이상을 감지하면 알림이나 재학습·롤백 같은 대응까지 자동으로 이어 줍니다."

```flow
데이터 수집·전처리 :: 업무의 결과로 생기는 데이터
모델 학습 :: 정확도·Loss 최적화
모델 아티팩트 :: 학습된 모델 파일
모델 서빙 (Day1) :: 실제 요청에 응답하는 운영 단계
모니터링 · AIOps (Day3) :: 자동 수집, 이상 탐지, 자동 대응
```

```compare
학습 (Training) | 서빙 (Serving)
실행 주기 | 1회성 배치 (수 시간~수 일) | 24시간 상시 (밀리초 단위)
핵심 지표 | Accuracy, Loss | Latency, Throughput, 가용성
실패 영향 | 재학습하면 됨 | 요청 즉시 실패 → 서비스 장애
자원 패턴 | 예측 가능한 배치 부하 | 예측 불가능한 트래픽 변동
실행 환경 | GPU 클러스터, 배치 스케줄러 | API 서버, 오토스케일링
장애 대응 | 실패 시 재실행 | 즉시 롤백·Fallback
```

- AIOps 3가지 가치: 자동 모니터링(사람이 계속 지켜보지 않아도 수집), 이상 탐지(느려짐·에러 급증 감지), 자동 대응(알림, 재시작·롤백)
- 과정 구조: HAIC 주가 예측 모델 하나를 Day1 서빙 → Day2 MLOps → Day3 AIOps 순서로 같은 서버 위에 쌓음

> [!tip] 실습에서 가장 크게 배운 것
> 모델이 틀려도 API는 200을 돌려준다. 드리프트 배치의 윈도우 RMSE가 6.43이어도 응답은 200이었다. 그래서 서빙 단계의 헬스체크·로깅이 곧 AIOps 감시의 기반이 된다.
