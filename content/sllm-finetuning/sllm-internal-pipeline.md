qa:
  - q: "상용 LLM API 대신 sLLM을 쓰는 이유는?"
    a: "가장 큰 이유는 데이터 주권이다. 상용 LLM은 요청 데이터가 벤더 인프라로 나가고, VPC 전용 인스턴스로 사내에 둬도 '학습에 사용하지 않음'은 계약일 뿐 기술적으로 검증하기 어렵다. 그래서 금융·의료·공공처럼 망분리 규제나 개인정보가 걸린 업무는 아키텍처로 외부 전송을 원천 차단하는 내부 sLLM을 쓴다. 여기에 반복 호출 비용, 초저지연·오프라인 요구, 사내 고유 지식 반영도 이유가 된다."
  - q: "LLM과 sLLM의 차이는?"
    a: "파라미터 규모가 LLM은 수백억~수조, sLLM은 수억~수십억 단위다. sLLM은 추론 비용과 지연이 낮아 저비용 인프라나 On-Device에서 돌릴 수 있고, PEFT로 싸게 커스터마이징할 수 있다. 대신 범용 지식이 얕아서 Fine-Tuning으로 도메인 지식, 응답 스타일, 사내 안전 정책을 주입해야 실무에 쓸 수 있다."

```compare
외부 파이프라인 (상용 LLM) | 내부 파이프라인 (sLLM)
흐름 | Client → API Gateway → GPT·Claude 등 | Client → 내부 Gateway → sLLM ↔ 사내 DB·문서
장점 | 강력한 범용 성능, 빠른 도입, 인프라 불필요 | 요청·응답이 사내망을 벗어나지 않음, 도메인 특화
약점 | 요청이 벤더 서버로 전송, 사내 지식에 약함 | 인프라 구축·운영 부담
보안 보증 | 계약서 의존 (블랙박스) | 아키텍처로 보증, 로그 전체 감사 가능
지식 | 넓지만 얕음 | 좁지만 깊음, 낮은 지연·비용
```

| 상용 LLM을 쓰기 어려운 상황 | 대표 산업·사례 |
|---|---|
| 망분리·보안 규제 (외부 연결 금지) | 금융, 국방, 공공 |
| 오프라인·현장 (네트워크 단절) | 제조 현장 설비 매뉴얼 Q&A, 선박·플랜트 |
| 초저지연 (API 왕복 불가) | 실시간 상담·제어 |
| 반복 호출 비용 누적 | 고빈도 내부 문서 처리 |
| 반출 금지 데이터 (PII·전문 용어) | 의료, 법률, 개인정보가 담긴 상담 로그 분류 |

> [!tip] 버티컬 sLLM이 갖춰야 할 5가지
> 도메인 지식 반영도, 추론 효율성, 데이터 프라이버시, 최신성 유지 용이성(낮은 재학습 비용), 안전한 출력 제어. 이 요건은 모델 크기가 아니라 Fine-Tuning으로 지식 주입·스타일 정렬·정책 반영이 이뤄질 때 완성됨.
