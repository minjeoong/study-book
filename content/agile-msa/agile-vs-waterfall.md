qa:
  - q: "Agile과 Waterfall의 차이는?"
    a: "Waterfall은 설계 → 개발 → 테스트를 순서대로 진행하고 요구사항을 초기에 확정해 변경을 최소화하려 한다. Agile은 짧은 Sprint를 반복하며 매번 동작하는 결과물(Increment)을 보여주고, 피드백으로 백로그 우선순위를 다시 정한다. 그래서 Waterfall은 결함과 변경이 후반에 발견될수록 수정 비용이 커지고, Agile은 리스크를 초기에 낮출 수 있다."
  - q: "Agile은 언제 잘 맞는가? 항상 좋은가?"
    a: "요구사항 변동성이 크고, 출시 후 반응을 보며 방향을 바꿔야 하고, 기능 단위로 쪼개 점진 릴리즈가 가능하고, PO와 개발팀이 상시 소통하는 소규모 팀일 때 잘 맞는다. 반대로 계약·규제로 요구사항이 고정된 프로젝트는 Waterfall이 나을 수 있다. 수업 사례인 FBI VCF는 두꺼운 요구사항 명세를 4년 넘게 그대로 지켰지만, 완성 시점에는 현장 요구가 바뀌어 실전 배치 없이 폐기됐다."
  - q: "Agile 도입이 실패하는 이유는?"
    a: "State of Agile Report 기준 1위가 Agile 가치·철학과 맞지 않는 조직 문화(63%)이고, 경험·스킬 부족(47%), 경영진 지원 부족(45%), 변화에 대한 저항(43%)이 뒤를 잇는다. 현장에서는 Sprint 이름만 쓰는 무늬만 Agile, PO 겸직으로 인한 의사결정 지연, 회고 없는 반복이 흔하다. 그래서 처음부터 전사 적용하지 않고 파일럿 팀으로 작게 시작해 검증한 뒤 확산한다."

```compare
Waterfall | Agile
개발 방식 | 순차적 (설계 → 개발 → 테스트) | 반복·점진적 (짧은 Sprint 반복)
요구사항 | 초기에 상세 확정, 변경 최소화 | 지속 수집·재우선순위화 (Backlog)
고객 피드백 | 프로젝트 종료 시점 | 매 Sprint Review
산출물 확인 | 최종 단계에 통합 결과물 | 매 Sprint 동작하는 Increment
변경 대응 | 비용 크고 절차 무거움 | 변경을 전제로 재계획
팀 구조 | 역할별 분업, 문서 기반 전달 | 교차기능팀, 짧은 피드백 루프
```

```flow
1. 현황 진단 :: 기존 프로세스·조직 문화 점검, 병목 파악
2. 파일럿 팀 선정 :: 자발적 참여 의사가 있는 1~2개 소규모 팀
3. Sprint 0 준비 :: 백로그 초안, Definition of Done 합의, 역할 지정
4. 첫 Sprint 실행 :: 1~2주 짧게 실행, Retro로 즉시 보정
5. 확산 & 정착 :: 성공 사례 공유 후 다른 팀으로 점진 확산
```

| 흔한 문제 | 증상 | 대응 |
| --- | --- | --- |
| 무늬만 Agile | Sprint 이름만 쓰고 실제는 Waterfall | 이벤트·산출물을 형식 아닌 목적대로 운영 |
| 역할 겸직 병목 | PO가 다른 업무와 겸직, 의사결정 지연 | PO 전담 배치, 일부 권한을 팀에 위임 |
| 회고 없는 반복 | Sprint만 돌고 프로세스 개선 없음 | Retro 액션 아이템을 다음 Sprint에 반드시 반영 |
| 과도한 문서화 병행 | Waterfall식 문서 프로세스 유지 | 필요한 산출물만, 대화·시각화 중심 |
| 진행상황 미가시화 | 아무도 상태를 모름 | Sprint Board, Burndown Chart로 매일 가시화 |

> [!tip] 면접 팁
> "Agile은 일하는 방식, MSA는 그걸 가능하게 하는 구조"로 묶어 말하면 두 주제가 한 번에 연결된다. 자주 고쳐 배포하려면 코드도 한 조각만 바꿔 배포할 수 있게 나뉘어 있어야 한다.
